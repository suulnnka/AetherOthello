## 一、结论速览

### 可以直接做(已实测,有正收益)

| # | 改动 | 效果 | 风险 |
|---|---|---|---|
| **1** | **8 方向填充改「提前收尾」+ 翻子跳过空方向**(已落地) | `moveFlips` **4.64×**、`genMoves` **1.55×**、`evaluate()` **1.24×**;节点数/着法/评分**逐位不变**;**代码净减 28 行** | 极低,数学等价,已过 **145 万项断言** |
| **2** | **残局「奇偶区域」排序 + 同区域翻子升序**(已落地,+46 行) | 完全求解节点数 **13 空 −36% / 14 空 −48% / 15 空 −36%**;残局求解**快约 2 倍**;着法与终局分**逐位不变** | 极低,只改排序键 |
| **3** | **估值加入前沿子(frontier)项**(已落地,+19 行) | 对弈得分率 **37.5% → 62.5%**(200 局 d5,约 **+89 Elo**);节点数 +13~19% | 中,**会改变棋力**(不再是"等价"改动) |

三项都已在生产代码里:`js/apps/reversi/index.js`,**775 → 811 行**。

### 不要做(已实测,收益≈0 或负)

| 改动 | 实测结果 |
|---|---|
| 惰性翻子(只算要搜的着法) | 节点 +6~11%,耗时净收益 ≈ **0** |
| 中局置换表 2^16 → 2^20(内存 +15MB) | 节点只降 **0.7~2.2%**,不划算 |
| 增量 Zobrist | `hashPos` 仅 **83ns**(占 4.6%),重构后仍需迭代翻子位,**净收益 <3%** |
| 用「潜在行动力」替换「实际行动力」 | **40 : 0 惨败**(见 §四.3),纯属假省钱 |
| **低层(depth 1)跳过排序** | 节点 **+10~14%**,每节点成本却不变 → 排序本身几乎免费(见 §五.2) |
| **估值「分阶段」**(子数差渐入 / 硬切换 / 三项全 taper) | 对基准版得分率只有 **26%~19%**(基准赢 73~81%,见 §五.3) |
| **对手行动力权重加倍** | 300 局 d5 = 53.7%,40 局 d6 = 50.0% → **未获确认,不建议采用** |

### 下一步值得做的大项(按预期收益排序)

1. **前沿子权重扫参(性价比最高)** —— 权重 `3` 是手调初值,没扫过。
   200 局 d5 只要 30 秒,扫 5 个档位约 3 分钟,很可能再挤出几十 Elo。
2. **残局求解器继续加固**:奇偶排序**已落地**(§3.3,−36%~−48%);
   剩下空区域连通分量、稳定子截断、根着法精排 ——
   这是**唯一能让"后期阶段"继续变强**的路(§五.4:优化后 14→15 空仍要
   **+244%**,15→16 空的量级仍不可接受,所以 `end` 阈值还抬不上去)
3. **ETC(增强置换表截断)**:展开子节点前先探一次表
4. **估值继续增强**:稳定子、X/C 方格条件权重
   —— 注意**不要**加"当前子数差"项,已实测有害(§五.3)
5. **Aspiration window**:迭代加深用上一轮分数开窗

### 关于「杀手剪枝」

**在黑白棋里基本无效,已实测(§五.2)。** 核心事实:低层排序**本身几乎不花时间**
(排序分搭在"为 makeMove 必需的翻子计算"上),却换来 10% 的节点节省 ——
去掉它节点反而 +10~14% 而时间不省。杀手剪枝在这个位置没有可换的收益。

## 二、成本模型(实测)

### 2.1 各原语单次耗时(`node bench/bench.mjs micro`)

### 2.3 结构性统计(`idstats`)

| 局面 | 叶子节点占比 | 置换表截断率 | 置换表给出最优着 |
|---|---|---|---|

  按占比折算约占**总时间的 16~20%**。它值得优化,但**不能靠削弱它**(见 §四.3)。
- **置换表截断率只有 3~6%**:看起来像"表没起作用",其实不是 ——

### 2.4 置换表到底值多少钱?(实测:别删)

> 前提说明:本引擎的置换表**本来就是跨轮复用的** —— `think()` 在迭代加深的各轮之间
> 不清表,一局棋内也不清表(§2.3 的 `idstats` 那组数据就是迭代加深下的命中率)。
> 所以那个 3~6% 的截断率不是"没复用"造成的漏水,而是这个搜索树里
> **转置局面的真实占比本身就低**(黑白棋的翻子依赖落子顺序,不像象棋那样
> 同一组着法的不同次序会稳定收敛到同一局面)。

把置换表探测与写入全部关掉:

| 局面 | 有置换表 | 无置换表 | 节点变化 |
|---|---|---|---|
| 空 48 深度 8 | 218,902 | 390,331 | **+78%** |
| 空 36 深度 8 | 181,886 | 450,584 | **+148%** |
| 空 20 深度 8 | 56,346 | 98,362 | **+75%** |

耗时(空 36):190ms → 410ms。

结论:置换表非常值钱,价值主要来自**把 TT 最优着排到队首**带来的排序提升,
而不是那 3~6% 的直接截断。**但扩表没用**:中局表从 2^16 扩到 2^20
(内存 +15MB)只能把节点数再降 0.7~2.2% —— 说明瓶颈不是表容量。

## 三、可以直接落地的三处改动

### 3.1 填充改「提前收尾」+ 翻子跳过空方向 —— 已落地,净减 28 行

**现状**:`fillE/W/S/N/SW/NE/SE/NW` 是**固定展开 6 层**的移位链(方向线上最多
6 个中间格)。不管实际有 0 个还是 1 个 O 子,每条都无条件跑满 6 层 ——
8 个方向合计 48 组「掩边列 + 移位 + 与」,而 `genMoves` 每次都要全算一遍。

**改法(两处,互补,不是替代关系)**:

1. **填充「走到不是 O 就停」**(改 8 个 `fill*` 内部):
   `let x = 第一步; while (x | xh) { t |= x; th |= xh; x = 下一步; }`
   方向线上有 O 才继续走,没有就一层都不展开。函数签名与调用方**全不动**,
   所以 `genMoves`、`moveFlips`、`evaluate()` **同时受益**。
2. **翻子跳过空方向**(改 `moveFlips`):每方向先就地判一次"邻格是否为 O"
   (就是该方向 fill 的第一步),落空则**连函数调用都不发生**。

为什么两处都要:`fill*` 的循环让 `genMoves`(每次调用算全部 8 方向)变快;
而 `moveFlips` 的调用点源格只有**一个**,邻格不是 O 的概率很高,
就地判断省掉的主要是**函数调用开销** —— 单靠循环版 `fill*` 省不掉这一层。

**实测**(`node bench/bench.mjs micro`,3 轮交错,以**四个版本共有的、
未被改动的 `hashPos` 作内部标尺**归一化后取中位数;数值 = 相对原版提速):

| 版本 | `genMoves` | `fillE ×1` | `evaluate()` | `moveFlips` |
|---|---|---|---|---|
| 原版 | 1.00× | 1.00× | 1.00× | 1.00× |
| 只加「跳过空方向」 | 1.03× | 1.12× | 0.75× | **3.82×** |
| 只加「提前收尾」 | 1.54× | 0.89× | 1.08× | 1.74× |
| **两处都加(已落地)** | **1.55×** | 0.87× | **1.24×** | **4.64×** |

端到端「8 层搜索 ns/节点」的最好一轮:原版 2036 → 落地版 **1059**。

> **为什么必须归一化**:本机噪声极大 —— `hashPos` 在四个版本里**代码完全相同**,
> 原始读数却在 **108~326ns** 之间摆了 3 倍。直接比绝对值会得到自相矛盾的结论
> (同一份改动,换个执行顺序就从"快 60%"变成"慢 60%")。用版本间共有的、
> 未改动的函数当标尺做比值,才能把信号从噪声里捞出来。**以后测任何微改动都该这样。**

**行数账**:`js/apps/reversi/index.js` **775 → 747 行(−28 行)**;
填充段 94 → 62 行,`moveFlips` 12 → 14 行。**加速的同时代码更短。**

**正确性证据**(四重):

1. **节点数完全一致**:`moves` / `endmoves` 两组固定局面的最佳着法、评分、
   **节点数**逐字相同。PVS 的节点数对排序极敏感,翻子有任何偏差,
   排序会变、节点数立刻漂移。
2. **通过项目自带测试**(读的就是生产文件)`node test/engine-test.mjs`:
   **1,451,341 项断言全部通过**,含 **约 49 万次随机局面翻子对拍**
   (与一份独立的 2D 数组朴素实现比对)和 **1320 局完全求解对拍**。
3. **两个改动各自单独验证过**:「提前收尾」与「跳过空方向」分别跑完
   145 万项断言,再合并成落地版。
4. 合并版补丁写入生产文件后**再测一次**:1,451,341 项全部通过。

改动后的代码就是 `js/apps/reversi/index.js` 里那 8 个 `fill*` 与 `moveFlips`。

### 3.2 估值加入「前沿子」项 —— 已落地,+19 行,约 +89 Elo

**现状**:`evaluate() = 位置权重差 + 行动力差 ×8`。没有前沿子、没有稳定子、
没有子数差,是偏"骨架"的估值。

**改法**:加入前沿子(frontier)项。前沿子 = **与空位相邻的己方棋子数**,
它衡量"暴露程度",**越少越好**。计算只需 8 次"走一格"再 popcount
(顺带一提,它用的就是上面 `expand8` 那套 8 向移位),比完整着法生成便宜
约 5 倍(实测单次约 25ns)。

```js
const frP = potMob(PLO, PHI, OLO, OHI);   // 己方前沿子
const frO = potMob(OLO, OHI, PLO, PHI);   // 对方前沿子
return s + (mobP - mobO) * 8 + (frO - frP) * 3;
```

**效果**(对弈台:双方各执黑一次,随机开局 4 手,得分率 = 胜 + 半和):

| 局数 / 深度 | 原估值 | 加前沿子 | 加前沿子的得分率 |
|---|---|---|---|
| 40 局 @ d5(早期) | 12 胜 | 27 胜 | 69% |
| 100 局 @ d5(早期) | 39 胜 | 59 胜 | 60% |
| 30 局 @ d6(早期) | 11 胜 | 17 胜 | 60% |
| **200 局 @ d5(定稿复测)** | 73 胜(4 和) | **123 胜** | **62.5%** |
| **60 局 @ d6(定稿复测)** | 21 胜(2 和) | **37 胜** | **63.3%** |

最后两行是在**填充加速 + 残局奇偶都已落地**的最终引擎上跑的:

```bash
node bench/duel.mjs bench/bench.mjs <加前沿子的版本> 200 5 4
```

两版之间**只差前沿子这一项**,所以这 ~13 个百分点的优势可以干净地归给它。

62.5% 得分率对应约 **+89 Elo**(200 局下 ±1σ ≈ 3.4 个百分点 ⇒ **+89 ± 19 Elo**),
深度 5 与深度 6 结果一致,不是噪声。

代价:节点数 **+13~19%**(前沿子项每节点多两次 `potMob`)。之所以划算,是因为
改动 1 已经把每节点成本压低了 —— 净效果是"棋力大幅提升,速度仍比优化前更快"。

权重 `3` 是手调的初值,尚未扫参;**这是目前最有把握的下一步增量**。

> 验证补充:`endnodes` 的残局节点数**完全没变** —— 这是对的,因为完全求解
> 走的是 `terminalDiff()`,根本不经过 `evaluate()`。这一条同时反证了
> 改动 3 只影响中局/启发式判断,没有意外污染残局路径。

### 3.3 残局「奇偶区域」排序 —— 已落地,+46 行

**现状**:完全求解(`exact`)时,着法排序用的还是中局那一套
`W64[格] + 翻子数 ×2`。这对残局是**双重不合适**:一是完全没用到"奇偶"这个
黑白棋终局最本质的结构;二是**翻子多在这里其实是坏事**(翻得多 = 暴露多 =
对手行动力大),却给了正权重。

**改法(两处,都只动排序键,不改任何一手的值)**:

1. **奇区域优先**:把空格按 8 连通切成若干区域,区域大小决定"谁在该区域走
   最后一步"——先走体积为**奇数**的区域。实现是对空格做位棋盘泛洪
   (8 连通膨胀迭代到不动点),给落在奇区域的着法加 `+1000`
   (远大于 W64 的 ±120 与翻子项的 ±36,所以它起主导作用)。
2. **同区域内翻子少的优先**:完全求解时把翻子项取负(`-fc` 而非 `+fc`),
   这是"对手行动力小"的廉价代理。

**实测**(完全求解节点数,5 个种子合并。**节点数是确定性的,完全无噪声**):

| 空 | 基线 | 只加奇偶 | **奇偶 + 翻子升序(已落地)** |
|---|---|---|---|
| 10 | 29,879 | −22% | **−26%** |
| 11 | 76,598 | −7% | **−17%** |
| 12 | 237,253 | −15% | **−20%** |
| 13 | 797,462 | −30% | **−36%** |
| 14 | 3,879,984 | −41% | **−48%** |
| 15 | 10,898,881 | −34% | **−36%** |

单局面耗时(14 空,5 种子合计):**4449ms → 2224ms,快约一倍**。

> 顺带否掉一个看起来更"直接"的改法:**只把翻子项取负、不加奇偶**
> —— 实测只有 −3%~−12% 且不单调,基本是噪声级收益(见上表思路的对照实验)。
> 起决定作用的是奇偶;翻子升序只是让同奇偶的着法之间排得更合理。

**为什么小空数上两个版本接近**:空数越少,整片空格往往就是一个连通块,
奇偶几乎不区分着法,此时排序主要靠第二关键字。13 空以上奇偶起主导作用,
差距才拉开。

**正确性**:`moves` / `endmoves` 与基线**逐字相同**(着法 + 评分 + 节点数),
`node test/engine-test.mjs` **145 万项断言全过**。
改动只在排序键上 ⇒ 完全求解的结果集合不变,这正是它风险极低的原因。

**顺带得到的三个旋钮(每处改一个数字)**:

| 旋钮 | 现值 | 说明 |
|---|---|---|
| 中级 `end` | 8 | 抬到 10 的代价仅约 **6ms/步**(10 空完全求解) |
| 高级 `end` | 14 | 抬到 15 后,15 空完全求解实测:平均 **1441ms**、P90 2180ms、**最慢 3643ms**(12 样本) |
| 奇偶权重 | 1000 | 只要远大于 `W64(±120) + 翻子(±36)` 即可,不必细调 |

要不要把 `end` 抬上去是**体验取舍**,不是技术问题:14 空现在平均
**434ms/步**,抬到 15 空就变成平均 **1441ms**、最慢 3.6s。代码默认保持 14。

## 四、性能层:已实测"不要做"的四件事

### 4.1 惰性翻子:净收益 ≈ 0

想只给"真正要搜的着法"算翻子(多数节点在头 1~2 步就截断了),为此需要
把翻子函数改成自包含(自己判断走完 O 之后是不是 P),代价是每方向多一次
移位与判断。同时静态排序分会丢掉「翻转数」这一项。

| 深度 | 节点数变化 | 基线 | 走格 | 惰性 |
|---|---|---|---|---|
| 5 | +6.1% | 21ms | 17ms | 17ms |
| 6 | +11.2% | 75ms | 72ms | **62ms** |
| 7 | +10.0% | 277ms | 203ms | **187ms** |
| 8 | +10.6% | 870ms | 703ms | 715ms |

排序变差让节点多了一成,把省下的算力又吃回去了,深度 8 反而是平手。
**结论:不做。** 排序质量比这点算力值钱。

### 4.2 扩大置换表:节点只降 0.7~2.2%

中局表 2^16 → 2^20(内存 +15MB,总占用从 ~17MB 到 ~31MB,会突破 README
里"≤20MB"的约束),节点数只降 0.7~2.2%。**不做。**

### 4.3 用「潜在行动力」替换「实际行动力」:灾难

动机很合理:`evaluate()` 里那两次 `genMoves` 占了 352ns 中的 260ns,
换成"与己方棋子相邻的空位格数"(潜在行动力,约 25ns)能让
`evaluate()` 直接降到 **124ns(-65%)**,节点数还会掉 37%。

**但节点数下降不代表变强** —— 估值特征变粗会让剪枝更激进,树小了,棋却可能更差。
用对弈台实测:

| 实验 | 局数 | 结果 |
|---|---|---|
| 潜在行动力(权重 ×3) vs 实际行动力(×8) | 10 局 @ d5 | **0 : 9**(1 和) |
| 潜在行动力(权重 ×8) vs 实际行动力(×8) | 40 局 @ d5 | **0 : 40** |

同权重下 **40 比 0**。所以"实际行动力(合法着数差)"是这个 AI 的**主要强度来源**,
它那 260ns 不是浪费。**这条是本文里最容易踩的坑:看到便宜的近似就换上去,
省下 65% 的估值耗时,棋力却直接归零。**

> 正确的方向是"**保留实际行动力的语义,同时降低它的成本**"(例如增量维护),
> 而不是用别的量替换它。

### 4.4 增量 Zobrist:收益 <3%,复杂度不低

`hashPos` 每节点扫描全盘所有棋子(约 28 子 → 83ns,占节点时间 4.6%)。
直觉上改成增量维护很划算,但要动就得把 Zobrist 从"行棋方相对颜色"改成
"黑/白绝对颜色 + 走子权"编码(否则换手时全盘颜色索引都要翻转,增量无从谈起),
然后在 make/unmake 里逐位异或翻子。而翻子只有 3~8 个,
增量版的单次成本与"扫一遍全盘子"是同一量级(只是常数小些),
净收益 <3%,却要在 `makeMove`/`unmakeMove`/`swapSides` 三处引入新的全局状态。
**性价比不足,不建议。**

## 五、算法层:A/B 对弈实测

> 本节全部结论来自 `bench/duel.mjs`:每局双方各执黑一次、随机开局 4 手,
> 得分率 = 胜 + 半和(和棋对双方各算半场)。100 局在深度 5 下的 ±1σ 约 5 个百分点。

### 5.1 「杀手剪枝」的结构性理由

你的直觉来自象棋,但两个棋的结构差异很大:

1. **象棋里 killer 有效,是因为存在大量"安静着法"** —— 安静着法好不好,
   无法从局面本身的静态特征判断,只能靠"这一步在别的节点引起过截断"来积累经验。
   黑白棋的每一步都必然落子、必然翻转,不存在安静着法;
   而一步棋好不好**可以直接从局面算出来**:是不是角、是不是 X/C 方格、
   翻几子、会不会把对手行动力喂大 —— 展开前全都能算。
2. **killer 依赖"同一着法在兄弟节点反复出现"**,象棋里"马跳到某格"会在成千上万个
   不同局面里反复成为杀着。黑白棋的落点与局面强绑定:盘面每步都在变、空位不断减少,
   同一个格子在相邻局面里的价值可能天差地别,所以 killer 表的命中率天然很低。
3. **实测佐证**:本项目置换表的**直接截断率只有 3~6%**,但关掉它节点数会
   **+75~148%** —— 说明它的价值主要来自「把 TT 最优着排到队首」,即
   妙着排序的贡献;而 TT 最优着本身就是"同一局面的历史经验",不需要跨局面的 killer。

**黑白棋里真正有效的排序手段**是(按收益):置换表最优着(已有)→
位置权重表(已有)→ 翻转数(已有)→ **残局奇偶(parity)排序** →
空区域连通分量 → ETC。

### 5.2 「低层不要排序、改用杀手剪枝」——实测是负收益

**你的设想的合理之处**:层数越浅、剩余深度越小,排序能换来的截断越少,
所以低层的排序看起来像浪费。

**但代码事实是:低层(depth === 1)节点的全部子节点都是叶子节点,必然各求一次值
—— 排序在那里不可能减少任何节点。** 于是问题变成:低层排序省下的运算量,
对比它避免掉的重复运算量。实测(去掉 depth===1 的排序与 TT 最优着前移,其余不动):

| 深度 | 基线节点 | 无低层排序 | 变化 |
|---|---|---|---|
| 5 | 18,463 | 21,010 | **+13.8%** |
| 6 | 60,804 | 69,149 | **+13.7%** |
| 7 | 200,034 | 222,285 | **+11.1%** |
| 8 | 684,352 | 752,095 | **+9.9%** |

节点数反而多了 10~14%。原因是 PVS 的零窗口机制:`depth===1` 时子节点求值
**总是精确的**(直接返回 `evaluate()`),父节点只在 `alpha < v < beta` 时才重搜
—— 排序正确时首着即最优,后续子节点几乎不会超过 α,重搜不发生;
乱序时大量子节点超过 α,同一个叶子被求值两遍。

**再算时间账**:每节点成本几乎没变(深度 8:1.538µs → 1.553µs)。
说明**低层排序本身的开销 ≈ 0** —— 排序分 `W64[sq] + 翻子数×2` 是搭在"算翻子"上的,
而**翻子为了 `makeMove` 本来就是必需的**,排序分只多一次 popcount 和一次表查。

所以:

- 低层排序**不是浪费**:它几乎免费,换来 10% 的节点节省 → **保留**。
- 杀手剪枝在低层**不可能赢**:它要么比静态序差(节点更多),要么一样(白搭),
  而且还要多维护 killer 表(额外时间)。上表其实给出了杀手剪枝在低层的**上界**:
  即使把排序质量退化到"完全不排序",时间也没省下来,节点却多了 10%。

### 5.3 「估值是否应该分阶段」——实测:任何"按阶段调权重"的版本都明显变弱

以当前最优的 frontier 版为基准,各跑 100 局:

| 方案 | 设计 | 结果(基准的得分率) |
|---|---|---|
| V2 平滑渐入 | `+ 子数差 × (26−空)×2`(空≥26 不计) | 基准 **73.5%** 胜 |
| V3 硬切换 | 空≤20 整段换成"重子数、轻行动力"(子数权重 30) | 基准 **80.0%** 胜 |
| V4 完整分阶段 | 行动力 / 前沿子 / 子数三项权重全随空位数变化 | 基准 **81.0%** 胜 |
| V6 子数项取负 | 同 V2 但把子数项符号反过来 | 基准 **90.5%** 胜 |

三个加子数项的方案全部惨败(73~90%),而且**取负比取正更差** ——
说明问题不在符号,而在"**在 15~26 空这个区间引入当前子数差**"这件事本身。

**为什么?** 这不是实现问题,而是黑白棋估值的一个基本性质:

- 当前子数差与**最终**点差的相关性,只在最后约 8~10 步才明显转正;
- 在那之前的中局,子多往往是**负担**(可被翻的子多、贴空位的前沿子多)。
  所以"子数差"在这个区间不是"弱特征",而是一个**方向都不对**的特征;
- 而估值真正负责的区间是 **15 空及以上**(14 空及以下已进入完全求解、返回精确点差)。
  也就是说:**子数差开始有效的区间,恰好已被搜索精确覆盖;估值负责的区间,
  恰好是子数差还没有效的区间。**

所以"分阶段"在黑白棋里的正确含义不是"每个阶段配一套权重表",而是
**用搜索把"子数差开始有效"的那一段吃掉**。这正解释了 V2/V3/V4 为何变弱:
它们强行把后期权重提前,让 AI 在中局开始贪子。

> 顺手测的"对手行动力权重加倍"(`mobP − 2×mobO`)在 300 局深度 5 下是 53.7%,
> 但 40 局深度 6 下是 50.0% —— **未获确认,不建议采用**。

### 5.4 后期阶段的正确改法:扩完全求解区间 —— 但先要修残局求解器

按 5.3 的结论,提升后期棋力的正路是把完全求解阈值从 14 空往上抬。
实测这个代价(**去掉预热排序的最坏情况**):

| 空位数 | 节点数 | 耗时 | 相对上一格 |
|---|---|---|---|
| 14 | 1,404,453 | 2.03s | — |
| 15 | 4,330,283 | 5.28s | **+208%** |
| 16 | 86,239,878 | 184.7s | **+1891%** |

> ⏱ 上表是**优化前**的数据。奇偶排序落地后(§3.3,5 种子合计):
> 14 空 388 万 → **201 万**,15 空 1089 万 → **694 万**;
> 但**每多一格仍要涨约 +244%**,所以 14→15 的墙钟仍是"平均 1.4 秒、最慢 3.6 秒"。
> 一句话:**奇偶让残局快了一倍,但还没有改变"阈值抬不上去"这个结构性障碍。**

也就是说**当时求解器每多算 1 个空格要涨 3~20 倍**(且强烈依赖于局面):
15 空就已经 5 秒(UI 上不可接受),16 空在一个局面上直接到 8624 万节点 / 185 秒。

**这就是结论的关键**:残局求解器的 parity / 空区域 / 稳定子截断**不是"锦上添花",
而是"把后期阶段做好"的前置条件**。这些技术在文献里的收益量级是 10~100 倍残局加速 ——
有了它们,阈值抬到 18~20 空才可行,15~20 空这段"估值盲区"才真正被消掉。
在此之前,任何在估值里手动补这一段的尝试(5.3 的四个方案)都是做无用功。

## 六、下一步值得做的大项

> 本节各条的具体收益**未实测**(依据是黑白棋社区的通行做法);
> 但 6.1 的**必要性**已被实测量化,见 §5.4。

### 6.1 残局求解器专项优化(唯一能让后期阶段真正变强的路)

> **进展:第 1 项(奇偶排序)已落地,见 §3.3 —— 14 空节点 −48%,残局求解快约一倍。**
> 下面剩下的几项尚未做。

当前 14 空要 201 万节点(优化前 388 万;均为 5 种子合计)。黑白棋残局求解是"排序质量决定节点数"
的典型场景 —— 根上排错一步,剪枝效率会成倍恶化。§5.4 已实测:优化前求解器
**每多 1 个空格涨 3~20 倍**(14→15 空 +208%,15→16 空 +1891%),
所以阈值抬不上去,**后期那一段就只能靠估值硬扛,而估值在那里恰好没有可用的
特征**(§5.3)。业界标准做法里:

- ✅ **奇偶排序(parity)**:已落地(§3.3)。这是公认最有效的一项。
- ⬜ **空区域连通分量**:只在局部连通的空区里算着法排序。已落地版本
  只在奇偶层面用了连通分量,更细的"区域内单独排序"还没做。
- ⬜ **最后 1~2 空的特判**:当前靠 `exact` 搜索自然处理,可以省掉节点开销。
- ⬜ **稳定子截断(stability cutoff)**:若稳定子数差已锁定胜负就直接返回。
  **注意成本**:稳定的迭代式稳定子算法单次约数千次运算,在 13~15 空
  (本项目的性能痛点区)稳定子很少能锁胜负,很可能**得不偿失**;
  它更适合 ≤10 空,而那段本来已经很快。要做先量收益。
- ⬜ **根着法排序**:除 2→4→6 预热外,可用「翻转数 + 角优先」精排。

已落地的奇偶排序本身带来 **−36%~−48%**(13~15 空)。**把阈值从 14 空抬到
18~20 空**仍是"后期阶段"的终极正解,但那需要稳定子等更强的手段,而目前
14→15 空仍有约 3.4 倍涨幅 —— 距离还很远。

### 6.2 ETC(增强置换表截断)

在展开一个节点的子节点之前,先对全部子局面的哈希做一次置换表探测;
若某个子节点已缓存了足够深、且能直接产生截断的分数,就在**不展开搜索**的情况下截断。
黑白棋文献里这是一项稳定的加速项。

### 6.3 估值继续增强

> **进展:前沿子(frontier)已落地(§3.2,约 +89 Elo);本节其余各项尚未做。**

- ✅ **前沿子(frontier)**:已落地。
- ⬜ **前沿子权重扫参**:权重 `3` 是手调初值,200 局 d5 只要 30 秒,优先做。
- ⬜ **稳定子(stable discs)**:角永远是稳定子;从角沿边线连续为己方的一段也是。
  稳定子**永远不可能被翻**,所以它是"最终子数"的下界 —— 这正是后期阶段
  真正需要的特征(而不是当前子数差,后者已实测有害,见 §5.3)。
  **注意成本**:迭代式稳定子算法单次数千次运算(详见 §6.1 的提醒)。
- ⬜ **X/C 方格条件权重**:当前 `W64` 对 X 方格(-40)、C 方格(-20)是**无条件**惩罚。
  但如果那个角已经被自己占了,这些格子其实不坏甚至很好 —— 改成条件权重更准确。
- ⬜ **稳定子 / 角的搜索延伸**:吃掉角的那一步延伸 1 层。

> ⚠️ 已实测排除的做法:取"当前子数差"按空位数渐入(§5.3)、把行动力/前沿子权重按
> 阶段 taper(§5.3)、对手行动力权重加倍(§5.3 末尾)。这三条**不要做**。

### 6.4 搜索侧

- **Aspiration window**:迭代加深时用上一轮分数 ± 小窗口开局,
  失败再放宽重搜。当前每次迭代都是全窗口起步。
- **根着法排序改进**:目前根排序用「位置权重 + 翻转数 ×2」,可以加"角优先 + 不给对手角"。

   代价不高,200 局 d5 只要 30 秒。
3. 前沿子让节点数 +13~19%。之所以现在仍划算,是因为改动 1 已把每节点成本压低;
   但若 UI 上的"思考时间"有硬预算,需要重新配平(加时间,还是整体缩放 `W64`)。
   **注意 `end` 阈值若从 14 抬到 15,这两项成本会叠加**(见 §3.3 的旋钮表)。
4. §六里各条的具体收益倍数都是**未实测的预期**,依据是黑白棋社区的通行做法;
   但其中的"必要性"已有实测支撑(§5.4)。
5. 对弈台的样本量:100 局深度 5 的 ±1σ 约 5 个百分点。
   要判定一个"小幅提升"(比如 +3 个百分点)需要数百局甚至上千局 ——
   本文的"未获确认"结论就是这么来的(§5.3 末尾的对手行动力加权在 300 局 d5 下
   看着有 3.7 个点的优势,但 40 局 d6 下完全没有)。
6. **§5.3 的四个估值方案都用了我手挑的权重**(如子数项 `(26−空)×2`、硬切换权重 30)。
   严格说,结论应该表述为"**这些量级的子数项/阶段切换是有害的;**权重小到
   不影响决策时自然也无害,但也无法证明有益"。要把"任何量级都没用"钉死,
   需要做权重扫参(每个权重跑数百局),代价不小。
7. **§5.2 的"低层排序"结论是在本引擎的具体排序分(`W64 + 翻子×2`)下成立的。**
   如果将来把排序分换成昂贵得多的形式(例如每步都要算一遍对手行动力),
   "低层排序几乎免费"这个前提就不成立了,届时值得重新评估低层策略。

### 实验脚本怎么复现

§5 里用到的 5 个实验版本都是一次性的,跑完已删除。要复现,直接以
`bench/bench.mjs`(= 当前生产引擎)为底,替换下面这几行即可,
然后用对弈台与它比较:

```js
// V1 低层跳过排序:把 search() 里的「插入排序 + TT 最优着前移」整块包进
//     if (depth > 1) { ... }

// V2 平滑渐入 / V6 取负(把末尾的 + 换成 -)
const discW = empty < 26 ? (26 - empty) * 2 : 0;
return s + (mobP - mobO) * 8 + (frO - frP) * 3 + (myDiscs - opDiscs) * discW;

// V3 硬切换
if (empty <= 20) return s + (mobP - mobO) * 2 + (frO - frP) + (myDiscs - opDiscs) * 30;

// V4 完整分阶段
const wMob = empty > 40 ? 10 : empty > 24 ? 8 : 4;
const wFr  = empty > 40 ? 4 : empty > 24 ? 3 : 2;

// V5 对手行动力权重加倍
return s + (mobP - mobO * 2) * 8 + (frO - frP) * 3;
```

对弈命令(100 局深度 5 约 30 秒):
